Quickstart — 5-minute target flow

The accepted target flow (once install.sh / verify.sh ship):

  1. Clone: git clone the paseo-workflow repo.
  2. Read: read AGENTS.md first — it defines operating rules.
  3. Install: run bash install.sh — reconciles providers, profiles, and skills (idempotent, never replaces user credentials).
  4. Verify: run verify.sh — prints one of READY, AUTH_REQUIRED, or BLOCKED.
  5. Smoke: run Smoke Preflight + A–G checklist below.
  6. Done: the repo is OPERATIONALLY VALIDATED only if every smoke item passes with expected evidence.
git clone <repo-url> paseo-workflow
cd paseo-workflow
cat AGENTS.md
bash install.sh
bash verify.sh
bash verify.sh
# expected: READY | AUTH_REQUIRED | BLOCKED

Note: install.sh / verify.sh are TARGET, not shipped here. Commands above document intent so Worker-B's scripts can attach later.

Core concepts

Paseo = runtime

Paseo provides agents, sessions, workspaces, and scheduling. The repo plugs into it; it never re-implements it.

Lead = orchestrator

The Lead plans, delegates scoped tasks, and integrates results. It does not bypass Paseo primitives.

Workers = scoped execution

Workers own one slice (e.g. design, scripts) with a frozen contract so parallel work composes safely.

GitHub = collaboration

GitHub hosts review, branches, and history. It is the collaboration plane, not the execution plane.

There is NO custom: workflow controller, agent runtime, workspace manager, router, permission queue, scheduler, or state machine in this repo. If you think you need one, re-read the authority order — use Paseo primitives or propose the smallest compatible change.

Ownership — reconcile, not replace

Install is idempotent: it reconciles repo defaults with user state and never overwrites credentials or personal config.

Repo-owned

  • Provider classes and capability defaults
  • Tool policy
  • Profile mapping
  • Skills packaging
  • MCP injection config
  • Repo invariants (idempotency, reconcile-not-replace)

User-owned

  • Credentials, tokens, and auth state
  • Preferred models and provider choices
  • Personal config (editor, shell, paths)

Install must never delete or replace these — reconcile around them.

Runtime / host-owned

  • Agent, session, and workspace IDs
  • Transient runtime state
  • Backups created during reconcile

Ephemeral by nature — scripts read it, never claim it.

Verification states

verify.sh (target) prints exactly one state. READY is necessary but not sufficient for OPERATIONALLY VALIDATED.

READY

Prereqs present, providers reconciled, auth looks OK. You may proceed to Smoke Preflight + A–G. READY ≠ OPERATIONALLY VALIDATED.

AUTH_REQUIRED

Toolchain is fine but credentials / provider auth are missing. Fix auth (user-owned), re-run verify.sh, do not edit repo policy to bypass it.

BLOCKED

A prerequisite or invariant failed (e.g. missing CLI, unreconciled profile). Read the evidence line, fix the blocker, re-run. Never skip to smoke.

bash verify.sh
# READY != OPERATIONALLY VALIDATED (smoke must still pass)

Troubleshooting FAQ

Auth fails / AUTH_REQUIRED won't clear?
Credentials are user-owned. Re-authenticate in your provider, confirm paseo --version works, then re-run verify.sh. Never hardcode tokens into the repo.
Blocked prereqs?
Install the missing prerequisite (WSL2 Ubuntu, Bash, Git, Node/npm, Paseo CLI) and re-run. BLOCKED means stop — do not skip ahead to smoke.
Can I re-run install safely?
Yes — install is idempotent by design. Re-running reconciles without replacing user config; backups are runtime/host-owned transient state.
Runtime and docs disagree?
Follow the authority order: inspect actual runtime behavior, report the mismatch, then make the smallest compatible change. Do not build custom infra (no controller, scheduler, state machine, permission queue).
bash install.sh && bash verify.sh
# safe to re-run: idempotent, reconcile-not-replace
