Paseo runtime, Lead orchestrates, Workers execute, GitHub collaborates.

A small static starter guide for the paseo-workflow repo. No backend, no build step — read, install, verify, smoke-test.

What this is

A 5-minute entry point for operators. It explains the shipped install flow, who owns what, and how to tell READY apart from OPERATIONALLY VALIDATED.

What this is not

Not a controller, runtime, or dashboard. Paseo is the runtime. This page only documents the shipped bootstrap flow.

Prerequisites

You need all of these before the shipped install flow can succeed:

  • WSL2 Ubuntu — supported host environment.
  • Bash — install and verify scripts run under Bash.
  • Git — clone the repo and track state.
  • Node / npm — required toolchain dependency.
  • Paseo CLI — the runtime CLI must be installed and reachable.
  • Codex CLI (external) — installed and authenticated by you on the host. The bootstrap detects and verifies it but never installs or upgrades it. A missing binary means BLOCKED.
  • OpenCode CLI (external) — installed and authenticated by you on the host. The bootstrap detects and verifies it but never installs or upgrades it. A missing binary means BLOCKED.

Quickstart — 5-minute shipped flow

The shipped flow:

  1. Clone: git clone https://github.com/khoawatt/paseo-workflow.git.
  2. Read: read AGENTS.md first — it defines operating rules.
  3. Dry run: run bash install.sh --dry-run to preview changes.
  4. Install: run bash install.sh — reconciles providers, profiles, and skills (reconcile-not-replace, never touches your credentials).
  5. Verify: run bash verify.sh — prints one of READY, AUTH_REQUIRED, or BLOCKED.
  6. Smoke: run Smoke Preflight + A–G checklist below.
  7. Done: OPERATIONALLY VALIDATED only if the full gate passes with observable evidence (Preflight + A–G, regression suite, live idempotency, secret-safety).
git clone https://github.com/khoawatt/paseo-workflow.git
cd paseo-workflow
cat AGENTS.md
bash install.sh --dry-run
bash install.sh
bash verify.sh
bash verify.sh
# expected: READY | AUTH_REQUIRED | BLOCKED

Note: Codex and OpenCode are external prerequisites you install and authenticate yourself — the bootstrap only detects and verifies them. Install is idempotent (reconcile-not-replace): a changed live config is backed up with mode 0600 under a timestamped name, and a no-op rerun creates no backup.

Core concepts

Paseo = runtime

Paseo provides agents, sessions, workspaces, and scheduling. The repo plugs into it; it never re-implements it.

Lead = orchestrator

The Lead plans, delegates scoped tasks, and integrates results. It does not bypass Paseo primitives.

Workers = scoped execution

Workers own one slice (e.g. design, scripts) with a frozen contract so parallel work composes safely.

GitHub = collaboration

GitHub hosts review, branches, and history. It is the collaboration plane, not the execution plane.

There is NO custom: workflow controller, agent runtime, workspace manager, router, permission queue, scheduler, or state machine in this repo. If you think you need one, re-read the authority order — use Paseo primitives or propose the smallest compatible change.

Profile mapping (per AGENTS.md): Lead → codex-lead; Planning / Research → opencode-worker; Implementation → codex-worker; Review → a fresh restricted session (prefer provider/model diversity from Implementation); Specialist → a domain-appropriate restricted provider/model.

Capability classes: the provider ID plus paseoTools defines the tool-capability boundary — workers run with paseoTools.enabled=false. Model strength never grants orchestration authority.

Authority order

When sources conflict, higher wins. Lower sources never override higher ones:

  1. 1. Runtime behavior — what Paseo actually does wins over everything written down.
  2. 2. Official docs — Paseo product docs second.
  3. 3. Execution brief — the tasking brief for this phase.
  4. 4. V0.2 specs — accepted design specifications.
  5. 5. Bootstrap policy — install/reconcile invariants.
  6. 6. AGENTS.md — repo operating rules; lowest of the six, still binding on agents.

Ownership — reconcile, not replace

Install is idempotent: it reconciles repo defaults with user state and never overwrites credentials or personal config.

Paseo-owned

  • Agent lifecycle, delegation, handoff, advisor, committee
  • Workspaces / worktrees, messages, permissions, schedules, heartbeats
  • Provider discovery, Profiles, and runtime state

Paseo is the orchestration runtime — the repo plugs into it, never re-implements it.

Repo-owned

  • Three required provider capability classes and owned profile routing/notes
  • MCP injection settings and native skill presence
  • Safe merge rules, bootstrap verification, and sanitized evidence
  • Repo invariants (idempotency, reconcile-not-replace)
  • install-project.sh is read-only: it never writes paseo.json

Human / host-owned

  • Codex and OpenCode installation, updates, executable selection, credentials, authentication
  • Model / thinking preferences and unrelated providers, profiles, and config
  • All high-impact approvals

Install must never delete or replace these — reconcile around them. Never commit live config, backups, credentials, auth state, session IDs, or private keys.

Verification states

verify.sh prints exactly one state. READY is necessary but not sufficient for OPERATIONALLY VALIDATED — the full gate also requires smoke Preflight + A–G, the regression suite, live idempotency, and secret-safety checks with observable evidence.

READY

Prereqs present, providers reconciled, auth looks OK. You may proceed to Smoke Preflight + A–G. READY ≠ OPERATIONALLY VALIDATED.

AUTH_REQUIRED

A required installed provider needs interactive human login. Follow that provider's native login flow, then rerun bash verify.sh. Never collect credentials or write them into the repo.

BLOCKED

A safety, policy, platform, missing external runtime, or other non-auth prerequisite failed — including a missing Codex or OpenCode binary. Read the evidence line for the next action, fix the blocker, re-run. Never skip to smoke.

bash verify.sh
# READY != OPERATIONALLY VALIDATED (full gate must still pass)
bash tests/test.sh
# fixture tests only — never prove live auth, discovery, or permissions

Keep evidence labels distinct: implemented, fixture-tested, runtime-tested, not tested / blocked. Fixture tests never prove live provider auth, MCP profile discovery, capability calls, worktree isolation, or permission behavior.

Troubleshooting FAQ

Auth fails / AUTH_REQUIRED won't clear?
Credentials are user-owned. Re-authenticate in your provider, confirm paseo --version works, then re-run verify.sh. Never hardcode tokens into the repo.
Blocked prereqs?
Install the missing prerequisite (WSL2 Ubuntu, Bash, Git, Node/npm, Paseo CLI, or the external Codex/OpenCode CLIs you manage yourself) and re-run. BLOCKED means stop — do not skip ahead to smoke.
Can I re-run install safely?
Yes — install is idempotent by design. Re-running reconciles without replacing user config; backups are runtime/host-owned transient state.
Runtime and docs disagree?
Follow the authority order: inspect actual runtime behavior, report the mismatch, then make the smallest compatible change. Do not build custom infra (no controller, scheduler, state machine, permission queue).
bash install.sh && bash verify.sh
# safe to re-run: idempotent, reconcile-not-replace
